# Git 提交信息规范参考

> 本文汇编业界**官方 / 权威**的 Git 提交信息（commit message）规范，供本项目参考。
> 每条规则均标注来源与权威性等级，便于核对原文。整理日期：2026-10-11。
> 修订 2026-10-11：**弃用 50/72 硬折行惯例**（见第 4 节），正文统一为「要点一条一行、不手动折行」。

---

## 0. 来源权威性说明（务必先看）

提交信息规范并非出自单一官方文档，而是由两套体系叠加而成。本文严格区分来源性质：

| 内容范畴 | 权威来源 | 官方性 |
|----------|----------|--------|
| 结构化前缀 `<type>(<scope>): <description>`、`feat` / `fix` / `BREAKING CHANGE` | **Conventional Commits 官方规范 v1.0.0** | ✅ 官方标准（有官方简体中文译文） |
| 扩展类型 `docs` / `style` / `refactor` / `perf` / `test` / `build` / `ci` / `chore` / `revert` | **Angular 提交约定**（经 `@commitlint/config-conventional` 固化）；Conventional Commits 规范正文明确引用 | ✅ Angular 官方贡献指南 |
| 标题（subject）与正文（body）分离、trailer 脚注格式 | **Git 官方文档**（git-scm.com `git-commit` / `git-interpret-trailers`） | ✅ Git 官方 |
| 首行简短（官方措辞：**建议**不超过 50 字符，非强制） | **Git 官方手册 `git-commit`** DISCUSSION 章 | ✅ Git 官方（"Though not required, it's a good idea…"） |
| 正文用 `-` 列表逐条列出、祈使句语气 | **本项目约定**（语气溯源见第 4.2 节） | ✅ 本仓库强制 |
| ~~正文按 72 列硬折行~~ **本项目不采纳**（存目见第 4.3 节） | **Tim Pope《A Note About Git Commit Messages》(2008)** | ❌ 社区惯例，**非 Git 官方**；中文按显示列宽折算后必然把句子断在半截 |

> 说明：Git 官方对首行的全部措辞只有一句建议 —— "Though not required, it's a good idea to begin the commit message with a single short (**no more than 50 characters**) line summarizing the change"（2026-10-11 核对 git-scm.com 原文）。**官方从未要求按列宽硬折行，被误传为"官方规定"的「72」完全出自 Tim Pope 2008 年那篇文章**（源于 80 列终端 + `git format-patch` 转邮件的旧场景）。中文一个字占 2 个显示列，72 列折算后约 36 个汉字，照此硬折行只能把句子断在半截。故本项目明确弃用，本文如实标注，请勿再以讹传讹。

## 1. 官方标准：Conventional Commits v1.0.0

- **英文原文（官方）**：<https://www.conventionalcommits.org/en/v1.0.0/>
- **简体中文（官方译文）**：<https://www.conventionalcommits.org/zh-hans/v1.0.0/>
- **繁体中文（官方译文）**：<https://www.conventionalcommits.org/zh-hant/v1.0.0/>
- **规范源码仓库（官方）**：<https://github.com/conventional-commits/conventionalcommits.org>

### 1.1 提交说明结构

官方英文原文：

```
<type>[optional scope]: <description>

[optional body]

[optional footer(s)]
```

官方简体中文译文：

```
<类型>[可选 范围]: <描述>

[可选 正文]

[可选 脚注]
```

### 1.2 核心结构元素（官方译文摘录）

1. **`fix:`** —— 类型为 `fix` 的提交表示在代码库中修复了一个 bug（对应语义化版本 SemVer 的 **PATCH**）。
2. **`feat:`** —— 类型为 `feat` 的提交表示在代码库中新增了一个功能（对应 SemVer 的 **MINOR**）。
3. **`BREAKING CHANGE:`** —— 在脚注中包含 `BREAKING CHANGE:`，或在 `<类型>(范围)` 后加 `!` 的提交，表示引入了破坏性 API 变更（对应 SemVer 的 **MAJOR**）。破坏性变更可以是任意类型提交的一部分。
4. 除 `fix:` 和 `feat:` 之外，也可以使用其它提交类型，例如 `@commitlint/config-conventional`（基于 Angular 约定）中推荐的 `build:`、`chore:`、`ci:`、`docs:`、`style:`、`refactor:`、`perf:`、`test:` 等。

### 1.3 规范条款（官方译文，节选关键条目）

> 关键词“必须（MUST）”“禁止（MUST NOT）”“应该（SHOULD）”“可以（MAY）”等的解释参考 RFC 2119。

1. 每个提交都**必须**使用类型字段前缀，它由一个名词构成（如 `feat`、`fix`），其后接**可选**的范围字段、**可选**的 `!`，以及**必要**的冒号（英文半角）和空格。
2. 当提交为应用或类库实现了新功能时，**必须**使用 `feat` 类型。
3. 当提交修复了 bug 时，**必须**使用 `fix` 类型。
4. 范围字段可以跟随在类型字段后面，**必须**是一个描述某部分代码的名词，并用圆括号包围，例如 `fix(parser):`。
5. 描述字段**必须**直接跟在 `<类型>(范围)` 前缀的冒号和空格之后，是对代码变更的简短总结。
6. 在简短描述之后，**可以**编写较长的提交正文，提供额外上下文；正文**必须**起始于描述字段结束的**一个空行之后**。
7. 提交正文内容自由编写，可用空行分隔不同段落。
8. 在正文结束的一个空行之后，**可以**编写一行或多行脚注；脚注格式受 `git trailer convention` 启发。
11. 破坏性变更**必须**在提交信息中标记：要么在 `<类型>(范围)` 前缀中用 `!` 标记，要么作为脚注的 `BREAKING CHANGE:` 项。
13. 若在前缀中用 `!` 标记破坏性变更，则脚注中可不写 `BREAKING CHANGE:`，同时描述部分应说明该破坏性变更。
14. 可以使用 `feat` 和 `fix` 之外的类型，例如 `docs: updated ref docs.`。
15. 工具实现**必须**不区分大小写地解析各信息单元，**唯独** `BREAKING CHANGE` 必须大写。

### 1.4 官方示例

**带描述与破坏性变更脚注：**
```
feat: allow provided config object to extend other configs

BREAKING CHANGE: `extends` key in config file is now used for extending other config files
```

**用 `!` 提示破坏性变更（含范围）：**
```
feat(api)!: send an email to the customer when a product is shipped
```

**不含正文：**
```
docs: correct spelling of CHANGELOG
```

**带范围：**
```
feat(lang): add Polish language
```

**多段正文 + 多脚注：**
```
fix: prevent racing of requests

Introduce a request id and a reference to latest request. Dismiss
incoming responses other than from latest request.

Remove timeouts which were used to mitigate the racing issue but are
obsolete now.

Reviewed-by: Z
Refs: #123
```

**revert（还原）提交：**
```
revert: let us never again speak of the noodle incident

Refs: 676104e, a215868
```

> 注：上例中的换行是**官方示例原文**（英文、且作者按自己的排版习惯断行）。本项目**不要求**照此手动断行，中文正文一律按第 4 节写法。

## 2. Angular 提交约定（扩展类型的权威出处）

Conventional Commits 只**强制** `feat` 与 `fix`；其余类型源自 **Angular 团队**的提交约定，并被 `@commitlint/config-conventional` 固化，是当前前后端领域最广泛采用的类型表。

- **Angular 官方贡献指南**：<https://github.com/angular/angular/blob/main/CONTRIBUTING.md>
- **commitlint 官方约定配置**：<https://github.com/conventional-changelog/commitlint/tree/master/@commitlint/config-conventional>

### 2.1 类型（type）一览

| 类型 | 含义 | SemVer 影响 |
|------|------|-------------|
| `feat` | 新增功能 | MINOR |
| `fix` | 修复 bug | PATCH |
| `docs` | 文档变更（README、API 文档等） | — |
| `style` | 代码样式调整（空格、缩进、分号等，不改逻辑） | — |
| `refactor` | 重构（既非新增功能也非修 bug） | — |
| `perf` | 性能优化 | PATCH |
| `test` | 增改测试用例 | — |
| `build` | 构建系统或外部依赖变更（如升级 Node、改依赖库） | — |
| `ci` | 持续集成配置变更（Travis、Jenkins、GitHub Actions 等） | — |
| `chore` | 杂项（非业务代码，如构建流程、工具配置） | — |
| `revert` | 回滚某次提交 | — |

> `BREAKING CHANGE`（破坏性变更）对应 MAJOR，可附着于任意类型。

## 3. Git 官方：标题 / 正文分离与 trailer 脚注

- **`git-commit` 官方手册**：<https://git-scm.com/docs/git-commit>
- **`git-interpret-trailers` 官方手册**：<https://git-scm.com/docs/git-interpret-trailers>
- **《Pro Git》官方书籍 · Contributing 章节**：<https://git-scm.com/book/en/v2/Distributed-Git-Contributing-to-a-Project>

`git-commit` 官方手册 DISCUSSION 章原文（2026-10-11 核对）：

> Though not required, it's a good idea to begin the commit message with a single short (no more than 50 characters) line summarizing the change, followed by a blank line and then a more thorough description. The text up to the first blank line in a commit message is treated as the commit title, and that title is used throughout Git. For example, git-format-patch[1] turns a commit into email, and it uses the title on the Subject line and the rest of the commit in the body.

要点：

- 首行简短（官方建议 ≤ 50 字符）只是 **good idea**，不是 MUST；官方**没有**任何列宽硬折行要求。
- **空行是硬性结构**：`The text up to the first blank line … is treated as the commit title` —— 缺空行会让后面全部文字都被当成 title，`git log --oneline`、`git shortlog`、`git rebase -i`、`git format-patch`、GitHub UI 都会跟着错。
- 脚注（如 `Refs:`、`Signed-off-by:`、`Closes:`）遵循 git trailer 格式，可用 `git interpret-trailers` 解析。

## 4. 正文写法、语气与弃用项

### 4.1 正文不硬折行（本项目强制）

- **正文不按字数或列宽手动断行**：一个段落写成一行；要点用 `-` 列表，一条一行。折行交给查看器（GitHub、IDE、`git log` 终端），它们会按窗口宽度自动折行。
- **理由**：手动硬换行是不可重排的硬断点 —— 窗口变窄会二次折行、变宽则留下参差不齐的短行，句子被断在半截，读者得在脑中拼接；它换来的收益只存在于 80 列纯终端与 `git format-patch` 转邮件的旧场景，对日常阅读是净损失。
- **禁止字面前缀**：不要写「标题：」「正文：」之类的标签行。首行必须直接是 `<类型>(<范围>): <描述>`，否则它不再是 Git 认定的 title，commitlint、changelog 生成器也无法解析。

### 4.2 语气：祈使句 / 现在时

- 写「新增 X」「修复 Y」，不写「新增了 X」「修复了 Y」「X 已修复」。
- 依据：`git merge`、`git revert`、`git cherry-pick` 自动生成的提交信息都是祈使句风格（如 `Merge branch 'x'`），人工提交与之统一，`git log` 连读才通顺。

### 4.3 弃用项存目（仅作来源澄清，不得据以改写正文）

原 Tim Pope《A Note About Git Commit Messages》(2008-04-19) 曾提出「首行不超过 50 字符、正文按约 72 列换行」：<https://tbaggery.com/2008/04/19/a-note-about-git-commit-messages.html>

- **性质**：社区惯例，**非 Git 官方规定**（官方只有第 3 节那句 good idea 建议）。
- **那个 72 是什么**：**显示列宽**，不是字符个数。80 列终端减去正文缩进与留白，余 72 列；一个汉字占 2 列，故折算后约 36 个汉字。
- **本项目结论**：**不采纳**，理由见第 4.1 节。此条仅作来源存目 —— 以后再遇到「按 72 列换行」的说法，一律按本节判为过时惯例，不得据此手动折行。

## 5. 落地写法（本文规范的合成结论）

将上述标准叠加，推荐格式：

```
<类型>(<范围>): <简短描述，祈使句，不加句号>

<正文：段落各占一行，不手动折行；要点用 - 列表，一条一行>

<脚注：Closes #123 / BREAKING CHANGE: ... / Refs: ...>
```

要点：

- 首行与正文之间、正文与脚注之间**必须空一行**（第 3 节）。
- 正文**不设字数 / 列宽上限，不手动断行**（第 4.1 节）；重点说清「为什么改」与「影响范围」，而不是复述代码。
- 首行句末不加句末标点（。！？）；正文与脚注正常使用标点。
- 首行不得出现「标题：」类字面前缀；正文不得出现「正文：」标签行。

### 中文项目示例

```
feat(ApexLab): 新增离合器踏板条与激进度滑块

回放层原来只有油门/刹车两根踏板条，无法体现手动挡换挡时的离合操作，也不能量化驾驶风格。

- 卡片增加第三根紫色离合条，100% = 完全踩下（分离）
- 离合只在换挡耗时内出现，此时驱动力为 0
- 新增激进度滑块，标定回放层的驾驶风格

数据源统一为 ApexSim.gearUpdate，避免两层各算一份导致口径不一致。
```

```
fix(auth): 修复 token 过期后未刷新导致的强制登出

拦截器原先只判断 401 状态码，未区分「token 过期」与「token 无效」，导致过期场景直接登出。

- 过期场景：先走 refresh 流程，刷新失败才登出
- 无效 token：维持直接登出，不做无谓重试

影响：登录后长时间挂起再操作不再被踢出。

Closes #142
```

### 提交前自检

1. 首行是 `<类型>(<范围>): <描述>`，无「标题：」类前缀，句末无标点。
2. 首行与正文之间、正文与脚注之间各有一个空行。
3. 正文没有按字数手动换行；要点是 `-` 列表，**一条一行**。
4. 「为什么改 / 影响范围」写在正文里，不是只罗列改了什么。
5. 脚注（`Closes` / `Refs` / `BREAKING CHANGE:`）位于最后，且未被硬折行拆开。
