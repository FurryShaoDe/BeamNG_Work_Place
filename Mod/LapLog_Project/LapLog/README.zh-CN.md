# LapLog

> 这是 `README.md` 的中文版。**两份文件必须一起改**；有歧义时以英文版为准（`README.md`）。

BeamNG.drive 的圈速记录模组。它采样位置、朝向、速度、驾驶输入与底盘遥测（四轮垂直接地载荷 + 车身 roll/pitch），
用你在地图上任意位置放置的起点门来切分圈速，把每一圈存到磁盘，并按「已保存起点」列出圈速与个人最佳。

它**不渲染任何东西**：没有 Ghost 车身、没有回放、没有尾迹、没有赛车线——LapLog 只是记录器与它的存档。
派生来源，以及相对上游删掉了什么，见 `NOTICE.md`。

## 安装

把 `LapLog` 文件夹复制到 BeamNG 用户目录下当前游戏版本的 `mods/`：

```
<BeamNG 用户目录>/<版本>/mods/LapLog/
```

然后在游戏里打开 **UI Apps**，添加 **LapLog**。

这个文件夹是**故意以未打包形式**使用的：它就是一个普通 mod 目录，游戏按挂载"解压后的 zip"的同一套流程挂载它；
不要把它打成 zip，也不要加 `mod_info/` 目录。

## 使用

1. 停在起圈位置，按 **设置起点**。门会放在车前方约 5 m、贴合地面，自动计圈进入布防状态——但此时还没有开始计时。
2. 开车穿过它。**第 1 圈就从这次过门开始计时**，与之后每一圈一样是"门到门"。在此之前，面板会把门状态显示为
   "等待通过起点门"，而不是显示一个正在跑的时钟。
3. 同方向再次穿过它即存下这一圈；下一圈自动开始，新的个人最佳立刻写入。
4. 打开面板，可以看到该起点下所有已存圈速。

**点到点**：在终点位置按 **设置终点**，这一圈就变成"起点门 → 终点门"（而不是"起点 → 起点"），并按真实用时保存。
**移除终点** 恢复为绕圈模式。

**一个起点门跑多条线路**：**在此新建线路** 会在同一个物理起点上再加一个圈速库，
所以多条线路可以共用一个起点而互不覆盖。

**手动录制**：**录制一段** 保存一段不带圈速的片段；它单独列出，永远不计入计时圈，也不参与个人最佳。

**车辆重置会丢弃本次尝试**：圈中按 <kbd>R</kbd> 或 <kbd>Insert</kbd> 会把样本丢掉并重新布防起点——
下一圈从下一次**正向过门**开始计时，而不是从车恢复的位置算。不会写入库文件，所以残圈池不会被失败尝试占满。
这是相对上游模组**唯一有意改变**的行为（上游会把每次中断都存成 `Incomplete` 残圈）。

## 计时精度

圈速时钟在物理步（`update`）上累加仿真时间，而**过门检测跑在渲染帧（`updateGFX`）**。
圈速 = "注意到过门"的那一渲染帧上的累加时钟；插值出来的过门点**只用于门的横向/纵向校验，从不用于修正时间**。
因此每次检测都晚 0 ~ 一帧。

实际操作中两次误差——起点检测与终点检测——来自同一机制，大部分互相抵消。用存档样本反推真实过门时刻
（首样本越过门平面的距离 ÷ 速度 = 起点滞后；末样本到门平面的距离 ÷ 速度 = 终点余量；
`lapTime − 末样本时间` = 检测滞后）实测：

| 圈 | lapTime | 起点滞后 | 终点余量 | 检测滞后 | 上报值 − 几何值 |
| --- | --- | --- | --- | --- | --- |
| hirochi 67.2 s | 67.205 | 6.3 ms | 0.0 ms | 4.5 ms | **−1.8 ms** |
| hirochi 63.7 s | 63.708 | 2.0 ms | 5.2 ms | 7.5 ms | **+0.3 ms** |
| smallgrid 25.4 s | 25.442 | 0.0 ms | 0.0 ms | 1.5 ms | **+1.5 ms** |

日常误差就是几毫秒量级。最坏情况仍受一帧渲染帧限制（60 fps 约 17 ms，掉帧或引擎卡顿时更大），
所以两圈相差不到 ~20 ms 时，请当成计时噪声。**采样不受这些影响**：样本带的是物理步累加的时间戳，
即使渲染帧率掉下去，采样网格依然规整。

**与上游行为相同。** Ghost Racer Enhanced 用同一套方式检测过门（`updateRecording` 从 `update` 调、
`updateAutoLap` 从 `updateGFX` 调，不做插值、approach latch 上也没有时间戳），所以这是继承来的、不是新引入的。
它的比赛 / Time Trial / Quick Race 模式不同：那里 `updateAutoLap` 返回 `raceControlled`，模组改记**游戏官方**圈速
（`historicTimes[].lapTime`、`onRaceWaypointReached(info.time)`、`onRaceResult(finalTime)`，经 `finishRaceLap` 交给 controller）。
LapLog 没有比赛集成，所以每一圈都走上面的估算方式。

**暂缓、未实现**：在起点布防时给 approach latch 打时间戳、并用 `amount` 反推过门时刻，
可以把最坏情况压到亚毫秒。因为实测误差已经只有几毫秒，所以只把它记录为可选项。

**起点门与录制起点对不上的圈**：正常圈的起点就是那次过门，所以首样本位于门平面后几厘米处，路径每圈**正向**穿过平面一次。
而早期"设置起点即开始录制"行为写下的记录可能从赛道中段开始：首样本已经在门后若干米，样本路径也从未正向穿过它。
这类记录的 `lapTime` 是从录制开始处算的，**不能与正常圈比较**。
逐圈速查：`signed(首样本) ÷ 速度` 接近 0 = 正常过门起圈；超过约 1 m 且样本里没有正向过门 = 起点门对不上。

## 数据写到哪里

路径相对于该关卡的存档目录：

```
lapLogs/freeRoam/<关卡>/startLines.json                       已保存起点注册表
lapLogs/freeRoam/<关卡>/<车辆>/starts/<id>/laplog.save.json
lapLogs/freeRoam/<关卡>/<车辆>/starts/<id>/laplog.save.library.json
lapLogs/freeRoam/<关卡>/<车辆>/starts/<id>/laplog.save.ghosts/<id>.json
lapLogs/vehicles/<车辆>/laplog.save.json                       手动录制库
lapLogs/vehicles/<车辆>/laplog.save.ghosts/<id>.json
```

手动录制库是**没有活动起点时**的回退位置：默认文件名是 `lapLogs/<vehicleDirectory>/laplog.save.json`，
而 BeamNG 的 `vehicleDirectory` 本身就是 `vehicles/<车辆>` —— 于是路径看起来重复了一次。
设置起点之前（或重置后没有活动起点时）录的短片会落在这里，本地查看器把它们单列在 `vehicles` 分组下。

这些路径刻意与 Ghost Racer 的 `ghostReplays/` 树完全分离，所以两个模组可以同时安装、不会互相抢文件。

每一圈是按采样率（默认 50 Hz）排列的扁平样本数组：

| 列号 | 字段 |
| --- | --- |
| 1 | 时间（s） |
| 2-4 | 位置 x, y, z |
| 5-7 | 车体前向 x, y, z |
| 8-10 | 上向 x, y, z |
| 11 | 速度（m/s） |
| 12 | 油门（0..1） |
| 13 | 刹车（0..1） |
| 14 | 挡位序号 |
| 15 | 手刹（0..1） |
| 16 | 离合（0..1） |
| 17 | 前左轮垂直接地载荷（N） |
| 18 | 前右轮垂直接地载荷（N） |
| 19 | 后左轮垂直接地载荷（N） |
| 20 | 后右轮垂直接地载荷（N） |
| 21 | 车身侧倾 roll（rad） |
| 22 | 车身俯仰 pitch（rad） |
| 23 | 转向输入（已过助力，−1..1，满舵 = ±1） |
| 24 | 转向输入（助力之前，−1..1） |

更早的 11 列样本仍可读取（它们只是没有输入数据）；format 3 的样本没有底盘遥测，format 4 的样本没有转向。
Ghost Racer Replay 1.2 / 1.6 的样本同样可读。列只会**尾部追加**，所以读取方永远可以按自己认识的列号取值、忽略其余的。

从 format 5 起，封装里还会带 **`steeringWheelLock`**（度，每次回放一个值）：第 23/24 列是归一化输入空间，
用锁角把它换算成方向盘角度——见下面 *转向（format 5）*。

## 底盘遥测（format 4）

四轮载荷来自 wheels 模块平滑后的轮胎垂直载荷（`wd.downForce`，单位 N），顺序固定为
**前左、前右、后左、后右**。轮位按**名字**匹配（`FL`/`FR`/`RL`/`RR`，与 BeamNG 自己用的名字一致，
例如 `wheels.wheelRotatorIDs`）；如果某辆车的轮子不叫这些名字，则回退到游戏自己的轮序，
面板标记仍然会说这条圈含底盘数据，但那辆车的角标可能对不上。缺失、损坏或离地的轮子记 0。

roll 与 pitch 直接取自 `obj:getRollPitchYaw()`，单位为弧度，**不做任何处理**——不滤波、不取反、不插值。
它们是**世界姿态**，不是车身相对路面的姿态：在有落差的地图上，pitch 几乎完全由车下的坡度决定。
实测一条 223 s 的山道圈（ks_nord，我们自己的记录）：pitch 与地形坡度的相关是 **+0.97**，
与纵向加速度只有 −0.10、与油门 +0.01、与刹车 +0.07。所以要看**悬架**俯仰，得先减掉坡度
（坡度可以从样本里还原：`pos_z` ÷ 水平里程，25 m 前瞻窗口就够——减掉之后 pitch 与纵向加速度相关 +0.27，
符号也自洽：加速抬头、刹车点头）。侧倾同样含路面横坡，但那部分从样本里还原不出来。
查看器已经替你做了这次减法（`grade` / `pitch_road` 两个派生通道）；记录器**有意**保存原始值，
因为坡度是赛道的属性，不是这一圈的属性。

采样成本：每个样本一次引擎调用（载荷是纯表读，数据由 `wheels.lua` 每个图形帧刷新一次，
所以在物理步采样时它们落后一帧——与所有从 `electrics.values` 读到的量同一新鲜度）。
这 6 列大约增加 35 字节/样本，约为 format 3 体积的 17%。

它们的用处：刹车/加速时的载荷转移（前后分配）、过弯载荷分布与内侧轮离地（左右分配）、
稳态气动/行驶载荷，以及作为悬架对转向与踏板输入的响应——车身侧倾/俯仰。

## 转向（format 5）

两列，都是归一化输入空间（**±1 = 满舵**，回正 = 0）：

- 第 23 列 = `electrics.values.steering_input`，即车辆**实际用来转向**的值
  （车辆输入模块把它与 `input.steering` 写在同一行，`lua/vehicle/input.lua:675-678`）；
- 第 24 列 = `electrics.values.steeringUnassisted`，同一信号在输入助力**之前**的取值
  （`input.lua:487-488`：understeer reduction、autocenter、slowdown assist）。
  两者之差就是助力介入了多少——这本身也是一项调校参考。

换成角度需要车辆的转向锁角：`角度 = 值 × steeringWheelLock`，锁角每次回放记一次、写在封装里
（来自 jbeam 的 `input.steeringWheelLock`，或由 hydros 模块为液压转向车回填，`input.lua:175-182`；
两者都没有时记录引擎自己的默认值 **450**，`input.lua:42`）。`输入 ±1` 对应 ±锁角，缺省时即 ±450°。
如果采样时两个来源只有一个有值（某个助力从未上报，或上下文里没有镜像值），
两列会都写同一个值，而不是在数组里留一个空洞。

引擎**没有**公开转向符号约定，而且两个 electrics 不同：`electrics.values.steering`
（度，仅液压转向车有）在 `hydros.lua:405` 是取反写入的，而 `steering_input` 保留输入符号，
引擎自己的 `tyreBarrier` 用 `sign(steering_input)` 算前轮转角。

**我们用自己的记录实测了（2026-10-04），因为这事不值得靠猜**：第 23 列（`steering_input`）
**正号 = 右转**。定标不是靠"记得的弯向"，而是靠左右轮载荷：`steering > 0` 的样本左轮载荷
多出约 9.6 kN（右转时左轮在外侧），两台车（Hirochi SBR、ETK 800）、三份记录完全一致。
同一个方法也定住了查看器的派生量 `g_lat`：它与（右 − 左）载荷相关 +0.88，也就是它的正号表示
"被推向右侧 / 左转"。两者因此天生相反，所以查看器的「反转转向方向」开关**默认已打开**：
打开后"正转向 = 左转 = 正 g"，平衡散点落在第一、三象限。
如果你换了一套输入栈来录制，请重跑这个定标（拿 `steering` 对 `load_fl+load_rl` 与 `load_fr+load_rr` 比），
而不是相信记忆里的方向。

成本：每个样本两个数字（约 12 字节，format 4 之上约 +5%）与两次 `electrics.values` 读，
即与踏板同样的"落后一帧"新鲜度。50 Hz 足够——转向是人手输入，真实内容只有 2–3 Hz。

真正的前轮转角没有 electrics 通道；引擎是用节点几何算的（`controller/tech/tyreBarrier.lua:26-31`），
以后若某个格式想记录车轮实际转角，照抄那条路径即可。

## 采样率

面板可选：20 / 30 / 50 / 100 Hz，默认 50（`DEFAULT_SAMPLE_RATE`、`MIN_SAMPLE_RATE`、`MAX_SAMPLE_RATE`）。
记录器在物理步上累加仿真时间，间隔到了就采一个样本。它**不会**为了追赶一次长帧而重复一个姿态，
所以网格在仿真时间上保持规整；请求高于物理步频率的采样率不会被兑现。

实测成本（一条真实 63.7 s 的圈）：format 3 布局下 202 字节/样本，即 50 Hz 时 630 KB、
100 Hz 时 1260 KB，约 10 与 20 KB/s 的行驶数据。format 4 的底盘列在此之上再加约 35 字节/样本
（未实测，按数字位宽估算）。查看器每圈的解析与通道构建为 20 与 40 ms，发给浏览器的载荷翻倍
（264 与 528 KB）。保存发生在圈结束的那一帧，所以文件体积翻倍也让那一瞬间的编码/写入成本翻倍。

实测收益（同一条圈）：把 50 Hz 记录重采样到 25 Hz、重算派生通道后比较——距离 0.00%、最高速 0.02%、
横向 G p99 0.90%、纵向 G p99 0.62%、峰值滑移角 0.15%、滑移曲线 RMS 差 0.03°。
把采样率减半只花掉约 1%，所以翻倍也只买到这么多。5 Hz 以上的内容占比：速度 0.08%、yaw rate 4.8%、
油门 11%、刹车 7%（是踏板阶跃与抖动，不是驾驶意图——人的踏板带宽只有 2–3 Hz）。

结论：对上列字段（**包括** format 4 的载荷与车身姿态——它们跟着悬架以几 Hz 变化）50 Hz 已经是 5–10 倍过采样，
而且圈速计时完全不依赖采样率。**只有**开始记录瞬态列（轮胎滑移、接地状态、悬架行程、损坏/碰撞）时才值得提到
100 Hz，那些量的内容在几十 Hz。另请注意：**改采样率改变的是文件体积与 PB/轨迹分辨率，不是圈速精度**。

## 存储上限

三个互相独立的配额，各 20 条：计时圈、残圈（未完成尝试）、手动录制。
满了以后：计时圈丢掉最慢的，残圈丢掉最短的（跑得最少的那个），手动录制丢掉最旧的。
用星标把某一行钉住，可以同时免于清理与删除。
